# Стандарт дизайна продуктов

> **Меньше, но лучше.** — Дитер Рамс

Здесь живёт наш стандарт того, как мы проектируем продукты. Ролевая модель — Дитер Рамс и его десять принципов хорошего дизайна. Цель — довести каждый продукт до уровня, где ничего лишнего, всё понятно, честно и сделано тщательно.

## С чего начать

| Задача | Что открыть |
| --- | --- |
| Понять, что от нас требуется | [STANDARD.md](STANDARD.md) — требования R1.1–R10.4 по десяти принципам Рамса |
| Привести существующий продукт в порядок | [checklists/AUDIT.md](checklists/AUDIT.md) → [отчёт аудита](templates/AUDIT_REPORT.md) |
| Начать новую функцию | [Описание решения](templates/SOLUTION_BRIEF.md) |
| Передать дизайн в разработку | [checklists/HANDOFF.md](checklists/HANDOFF.md) |
| Выпустить изменение | [checklists/RELEASE.md](checklists/RELEASE.md) |
| Зафиксировать спорное решение | [Запись решения](templates/DECISION_RECORD.md) |
| Отступить от обязательного требования | [Исключение](templates/EXCEPTION.md) |

## Как устроено

```
Знания (зачем)     principles/   — Рамс как основа, HIG и Айв как вспомогательные источники
Стандарт (что)     STANDARD.md   — проверяемые требования с ID, уровни качества, приоритеты
Процесс (когда)    checklists/   — аудит, передача в разработку, выпуск
                   templates/    — описание решения, запись решения, исключение, отчёт аудита
```

**Знания** объясняют, почему мы так работаем:

- [Принципы Дитера Рамса](principles/RAMS_PRINCIPLES.md) — основа стандарта: смысл каждого принципа, примеры, налог на ценность, разбор компромиссов.
- [Apple Human Interface Guidelines](principles/HIG_GUIDE.md) — конкретные решения: навигация, поиск, модальные окна, формы, обратная связь.
- [Подход Джони Айва](principles/IVE_DESIGN_GUIDE.md) — исследование, описание поведения словами, прототипирование и проверка с людьми.

**Стандарт** превращает принципы в требования, которые можно проверить и на которые можно сослаться в ревью: «нарушает R6.1».

**Процесс** встраивает проверки в работу: до макета, перед разработкой, перед выпуском и при аудите существующих продуктов.

## Как довести продукт до уровня «Меньше, но лучше»

1. Выбрать 3–5 ключевых сценариев продукта.
2. Пройти их по [чек-листу аудита](checklists/AUDIT.md) в реальных условиях: реальные данные, клавиатура, медленная сеть, увеличение 200%.
3. Завести каждую находку задачей с ID требования и серьёзностью P0–P3.
4. Исправить по порядку: P0 → P1 → P2 → P3.
5. Повторить аудит и сравнить с исходным протоколом.

| Уровень | Условие |
| --- | --- |
| 1. Работает | Нет блокеров P0 |
| 2. Понятно и честно | Нет P0 и P1, все обязательные требования выполнены |
| 3. Меньше, но лучше | Плюс рекомендованные требования, измеренный налог на ценность и проверка с людьми |

## Подключение к репозиторию продукта

Скопируйте из [templates/github/](templates/github/) в `.github/` репозитория продукта:

- `pull_request_template.md` — пункты стандарта в каждом PR;
- `ISSUE_TEMPLATE/audit-finding.md` — находки аудита;
- `ISSUE_TEMPLATE/solution-brief.md` — описание решения до макета.

## Правила редактирования

- Принципы принадлежат Рамсу; требования и методы — наша интерпретация. Не приписываем Рамсу, Айву или Apple то, чего они не говорили.
- Новое требование должно иметь способ проверки и ссылку на принцип.
- Изменения стандарта фиксируются в [CHANGELOG.md](CHANGELOG.md) с повышением версии.
