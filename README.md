# Стандарт дизайна продуктов

> **Меньше, но лучше.** — Дитер Рамс

Здесь живёт наш стандарт того, как мы проектируем продукты. Он опирается на три источника — принципы Дитера Рамса, подход Джони Айва и Apple Human Interface Guidelines — и проверяется двумя независимыми проверками: ИИ и человеком, по одному и тому же списку критериев.

## Три источника

| Источник | Что даёт |
| --- | --- |
| **Дитер Рамс** | Что такое хороший продукт. Десять принципов — структура стандарта |
| **Джони Айв** | Как мы приходим к решению: описание словами, прототип, проверка без объяснений, ответственность после выпуска |
| **Apple HIG** | Как решать конкретные взаимодействия: навигация, поиск, модальные окна, кнопки, поля, прогресс, тексты, доступность |

У каждого требования видно, на что оно опирается. Полная картина — в [карте источников](checklists/SOURCES.md).

## Две проверки

```
                 ┌─ ИИ-проверка: Claude по скриншотам и описанию ─┐
Макет готов ─────┤          одни и те же критерии «да/нет»         ├──→ Сверка ──→ Вердикт
                 └─ Проверка человеком: ревьюер по прототипу ─────┘
```

- У каждого из 54 требований есть 2–7 **критериев** — коротких утверждений вроде «Ошибка показана у того поля, к которому относится». На каждый отвечают «да» или «нет». Итог пункта считается сам.
- Человек отвечает первым и не видит ответ ИИ, пока не ответил сам.
- Если ИИ нашёл проблему, а человек нет, человек либо меняет ответ, либо отклоняет находку ИИ с записанной причиной.
- Вердикт выносит человек, и только после обеих проверок.

Подробно — в [инструкции по двум проверкам](checklists/TWO_CHECKS.md).

## Без признаков ИИ-дизайна

ИИ без решения рисует среднее из того, на чём учился: фиолетовые градиенты, одинаковые карточки, подписи-инструкции под заголовками. Мы собрали эти признаки в [список](checklists/AI_TELLS.md) (И1–И42) и не делаем их по умолчанию, кто бы ни рисовал. Следят за этим R4.8, R7.6 и R10.1, а в Claude Code — скилл `design-make`, который рисует по стандарту и проверяет себя по списку.

## Пройти проверку

| Формат | Где | Для чего |
| --- | --- | --- |
| **Интерактивный чек-лист** | [открыть на claude.ai](https://claude.ai/artifact/WSYyZYb4m6B61DDmGVyGyw) · исходник `site/checklist.html` | Человек отмечает критерии, ИИ-проверка запускается прямо там по скриншотам или загружается из ответа Claude. Сверка, вердикт, отчёт, задачи, история команды |
| **Рабочий лист** | [checklists/WORKSHEET.md](checklists/WORKSHEET.md) | Тот же список как документ: прочитать, распечатать, пройти с ручкой |
| **Claude Code** | `/design-check` в этом репозитории | ИИ-проверка со скриншотами и отчётом; результат загружается в интерактивный чек-лист |

| Проверка | Пунктов | Кто проверяет | Когда |
| --- | --- | --- | --- |
| Дизайн-ревью | 50 | человек + ИИ | Макет перед передачей в разработку — главная проверка |
| Быстрая проверка | 15 | человек, ИИ по желанию | Прогнать макет на ходу; не заменяет ревью |
| Приёмка сборки | 27 | человек + ИИ | Работающая сборка против макета перед выпуском |
| Аудит продукта | 54 | человек + ИИ | Существующий продукт |

Интерактивный чек-лист открывается только у тех, с кем им поделились через меню «Поделиться» на странице. Чтобы сохранять проверки в историю, нужен доступ «Участник» или выше.

## Дизайн идёт первым

Мы сначала проектируем, потом разрабатываем. Поэтому главная проверка происходит в макете, до кода: 50 из 54 требований либо полностью проверяются в макете, либо должны быть в нём спроектированы и описаны.

```
Описание решения → Макет → ДИЗАЙН-РЕВЬЮ → Передача → Разработка → Дизайн-приёмка → Выпуск
                            человек + ИИ                           человек + ИИ
```

**Знания:**

- [Принципы Дитера Рамса](principles/RAMS_PRINCIPLES.md) — смысл каждого принципа, примеры, налог на ценность, разбор компромиссов.

## Как довести продукт до уровня «Меньше, но лучше»

1. Выбрать 3–5 ключевых сценариев продукта.
2. Провести аудит двумя проверками: человек — по [чек-листу аудита](checklists/AUDIT.md) в реальных условиях, ИИ — по скриншотам.
3. Завести каждую находку задачей с ID требования и серьёзностью P0–P3.
4. Исправить по порядку P0 → P1 → P2 → P3, каждое исправление — сначала в макете, через дизайн-ревью.
5. Повторить аудит и сравнить с исходным протоколом.

| Уровень | Условие |
| --- | --- |
| 1. Работает | Нет блокеров P0 |
| 2. Понятно и честно | Нет P0 и P1, все обязательные требования выполнены |
| 3. Меньше, но лучше | Плюс рекомендованные требования, измеренный налог на ценность и проверка с людьми |

## Подключение к репозиторию продукта

Скопируйте из [templates/github/](templates/github/) в `.github/` репозитория продукта:

- `pull_request_template.md` — пункты стандарта в каждом PR;

- `ISSUE_TEMPLATE/solution-brief.md` — описание решения до макета.

## Как устроен чек-лист

Один источник правды:

- `STANDARD.md` — нормативный текст, уровень и этап каждого требования;
- `checklist/items.toml` — критерии для человека и ИИ, вопросы, подсказки, тревожные признаки, источники (Айв, HIG, W3C), порядок прохождения;
- `checklist/ai_protocol.toml` — правила ИИ-проверки и формат ответа.

`python3 scripts/build_checklist.py` сверяет файлы и собирает `site/checklist.html`, `checklists/WORKSHEET.md` и `checklists/SOURCES.md`. Если требование есть в стандарте, но не описано в чек-листе (или наоборот), сборка падает. CI проверяет, что собранные файлы не устарели. После сборки опубликуйте страницу заново, чтобы обновить интерактивную версию.

`python3 scripts/build_checklist.py --ai-prompt design` печатает полное задание для ИИ-проверки — то же, что использует страница.

## Правила редактирования

- Принципы и рекомендации принадлежат авторам; требования, критерии и методы — наша интерпретация. Не приписываем Рамсу, Айву или Apple то, чего они не говорили.
- Новое требование должно иметь критерии, способ проверки и ссылку на принцип.
- Изменения стандарта фиксируются в [CHANGELOG.md](CHANGELOG.md) с повышением версии.
