# Стандарт дизайна продуктов

> **Меньше, но лучше.** — Дитер Рамс

Здесь живёт наш стандарт того, как мы проектируем продукты. Ролевая модель — Дитер Рамс и его десять принципов хорошего дизайна. Цель — довести каждый продукт до уровня, где ничего лишнего, всё понятно, честно и сделано тщательно.

## Дизайн идёт первым

Мы сначала проектируем, потом разрабатываем. Поэтому главная проверка по стандарту происходит в макете, до кода: 44 из 48 требований либо полностью проверяются в макете, либо должны быть в нём спроектированы и описаны.

```
Описание решения → Макет → ДИЗАЙН-РЕВЬЮ → Передача → Разработка → Дизайн-приёмка → Выпуск
                    по требованиям    главная        короткий                сборка против
                    к файлу           проверка       барьер                  макета
```

## Пройти чек-лист самому

| Формат | Где | Для чего |
| --- | --- | --- |
| **Интерактивный чек-лист** | [открыть на claude.ai](https://claude.ai/artifact/WSYyZYb4m6B61DDmGVyGyw) · исходник `site/checklist.html` | Выбрать проверку, отметить пункты, получить вердикт, скопировать отчёт и задачи. Проверки сохраняются в общую историю команды |
| **Рабочий лист** | [checklists/WORKSHEET.md](checklists/WORKSHEET.md) | Тот же чек-лист как документ: прочитать, распечатать, пройти с ручкой |

Оба формата устроены одинаково: пункты идут в порядке, в котором их удобно проверять (задача → первый взгляд → сценарий → тексты → ошибки → реальные данные → система → доступность → результат). У каждого пункта простой вопрос, способ проверить его за минуту и тревожный признак нарушения. Для макета и для работающего продукта вопросы разные.

| Проверка | Пунктов | Когда |
| --- | --- | --- |
| Дизайн-ревью | 44 | Макет перед передачей в разработку — главная проверка |
| Быстрая проверка | 12 | Прогнать макет на ходу; не заменяет ревью |
| Приёмка сборки | 25 | Работающая сборка против макета перед выпуском |
| Аудит продукта | 48 | Существующий продукт |

Чек-лист открывается только у тех, с кем им поделились через меню «Поделиться» на странице. Чтобы сохранять проверки в историю, нужен доступ «Участник» или выше.

## Как устроено

```
Знания (зачем)     principles/   — Рамс как основа, HIG и Айв как вспомогательные источники
Стандарт (что)     STANDARD.md   — проверяемые требования с ID, уровни качества, приоритеты
Процесс (когда)    checklists/   — дизайн-ревью, передача, дизайн-приёмка и выпуск, аудит
                   templates/    — описание решения, файл макета, запись решения, исключение, отчёт аудита
```

**Знания** объясняют, почему мы так работаем:

- [Принципы Дитера Рамса](principles/RAMS_PRINCIPLES.md) — основа стандарта: смысл каждого принципа, примеры, налог на ценность, разбор компромиссов.
- [Apple Human Interface Guidelines](principles/HIG_GUIDE.md) — конкретные решения: навигация, поиск, модальные окна, формы, обратная связь.
- [Подход Джони Айва](principles/IVE_DESIGN_GUIDE.md) — исследование, описание поведения словами, прототипирование и проверка с людьми.

**Стандарт** превращает принципы в требования, которые можно проверить и на которые можно сослаться в ревью: «нарушает R6.1».

**Процесс** встраивает проверки в работу: до макета, на дизайн-ревью, перед разработкой, при приёмке сборки и при аудите существующих продуктов.

## Как довести продукт до уровня «Меньше, но лучше»

1. Выбрать 3–5 ключевых сценариев продукта.
2. Пройти их по [чек-листу аудита](checklists/AUDIT.md) в реальных условиях: реальные данные, клавиатура, медленная сеть, увеличение 200%.
3. Завести каждую находку задачей с ID требования и серьёзностью P0–P3.
4. Исправить по порядку P0 → P1 → P2 → P3, каждое исправление — сначала в макете, через дизайн-ревью.
5. Повторить аудит и сравнить с исходным протоколом.

| Уровень | Условие |
| --- | --- |
| 1. Работает | Нет блокеров P0 |
| 2. Понятно и честно | Нет P0 и P1, все обязательные требования выполнены |
| 3. Меньше, но лучше | Плюс рекомендованные требования, измеренный налог на ценность и проверка с людьми |

## Подключение к репозиторию продукта

Скопируйте из [templates/github/](templates/github/) в `.github/` репозитория продукта:

- `pull_request_template.md` — пункты стандарта в каждом PR;
- `ISSUE_TEMPLATE/audit-finding.md` — находки аудита;
- `ISSUE_TEMPLATE/solution-brief.md` — описание решения до макета.

## Как устроен чек-лист

Один источник правды — два слоя:

- `STANDARD.md` — нормативный текст, уровень и этап каждого требования;
- `checklist/items.toml` — человеческий слой: вопрос, как проверить, тревожный признак, порядок прохождения.

`python3 scripts/build_checklist.py` сверяет оба файла и собирает из них `site/checklist.html` и `checklists/WORKSHEET.md`. Если требование есть в стандарте, но не описано в чек-листе (или наоборот), сборка падает. CI проверяет, что собранные файлы не устарели. После сборки опубликуйте страницу заново, чтобы обновить интерактивную версию.

## Правила редактирования

- Принципы принадлежат Рамсу; требования и методы — наша интерпретация. Не приписываем Рамсу, Айву или Apple то, чего они не говорили.
- Новое требование должно иметь способ проверки и ссылку на принцип.
- Изменения стандарта фиксируются в [CHANGELOG.md](CHANGELOG.md) с повышением версии.
