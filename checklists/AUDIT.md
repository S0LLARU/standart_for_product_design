# Аудит продукта по стандарту

> Пройти самому: [интерактивный чек-лист](https://claude.ai/artifact/WSYyZYb4m6B61DDmGVyGyw) с вердиктом и отчётом или [рабочий лист](WORKSHEET.md) для чтения и печати. Пункты там те же, с вопросами простым языком и подсказками, как проверить.

Главный рабочий инструмент: проходим продукт по чек-листу, находим всё, что не дотягивает до [стандарта](../STANDARD.md), и доводим продукт до уровня «Меньше, но лучше».

Аудит проводится по сценариям, а не по экранам. Экран может выглядеть безупречно и при этом не давать человеку закончить задачу.

## Порядок аудита

### 1. Выбрать сценарии

Выбираем 3–5 ключевых сценариев продукта: самые частые и самые дорогие при ошибке. Для каждого записываем:

- кто действует и в какой ситуации;
- момент получения ценности — например, «человек нашёл нужный файл и убедился, что это актуальная версия»;
- путь: от первого намерения до использования результата вне продукта.

### 2. Подготовить условия

- реальные или реалистичные данные: длинные названия, пустые списки, сотни записей, пользовательские изображения;
- целевые устройства и ширины экрана: десктоп и телефон для веба;
- клавиатура без мыши, увеличение до 200%, настройка уменьшения движения;
- медленное и отключённое соединение;
- автопроверка доступности (axe или Lighthouse) для каждого экрана сценария.

### 3. Пройти сценарии и записать налог на ценность

Проходим каждый сценарий полностью, включая ошибку, отмену, возврат и повторный вход. Для каждого сценария фиксируем:

| Затраты | Что записываем |
| --- | --- |
| Действия | Повторный ввод, лишние переходы, обходные пути |
| Поиск глазами | Где несколько одинаково заметных элементов, где команда не на своём месте |
| Размышление | Выбор между неясными вариантами, непонятные термины |
| Память | Что нужно помнить с другого экрана |
| Ожидание | Блокирующая загрузка, неопределённость результата |
| Исправление | Что приходится повторять после ошибки |
| Неуверенность | Где приходится перепроверять, произошло ли действие |

Числа в один балл не складываем. Для сравнения «до» и «после» используем отдельные показатели: успешность, время до результата, ошибки, возвраты.

### 4. Пройти чек-лист

Для каждого пункта ниже ставим отметку и прикладываем доказательство: скриншот, запись экрана или шаги воспроизведения.

| Отметка | Значение |
| --- | --- |
| ✅ | Соответствует — проверено в работающем продукте |
| ⚠️ | Частично — соответствует не во всех сценариях |
| ❌ | Не соответствует |
| н/п | Не применимо — с объяснением, почему |

### 4а. Провести ИИ-проверку

Параллельно Claude проверяет те же пункты по скриншотам сценариев. Расхождения разбираем по [инструкции по двум проверкам](TWO_CHECKS.md): каждую находку ИИ подтверждаем или отклоняем с причиной.

### 5. Завести находки

Каждый ⚠️ и ❌ становится отдельной задачей по [шаблону находки](../templates/github/ISSUE_TEMPLATE/audit-finding.md): ID требования, сценарий, шаги, серьёзность P0–P3 по [таблице приоритетов](../STANDARD.md#приоритет-исправлений), предлагаемое направление исправления.

### 6. Составить отчёт и план

Заполняем [отчёт аудита](../templates/AUDIT_REPORT.md), определяем текущий [уровень качества](../STANDARD.md#уровни-качества-продукта) и план: сначала все P0, затем P1, затем P2 и P3 партиями по сценариям.

Исправления идут тем же путём, что и любая работа у нас — сначала дизайн:

1. находка → исправление в макете по [требованиям к файлу](../templates/DESIGN_FILE.md);
2. [дизайн-ревью](DESIGN_REVIEW.md) исправленного сценария;
3. [передача в разработку](HANDOFF.md);
4. дизайн-приёмка сборки по [чек-листу выпуска](RELEASE.md).

Заодно проверяем, почему проблема дошла до продукта: какого состояния или аннотации не было в макете. Это показывает, что усилить на дизайн-ревью.

### 7. Повторить

После исправлений проходим те же сценарии в тех же условиях и сравниваем с исходным протоколом. Для уровня 3 добавляем наблюдение за 3–5 людьми, выполняющими задачи без подсказок автора.

## Чек-лист

### 1. Инновационность

- [ ] **R1.1** У каждой нестандартной механики и автоматизации есть понятное затруднение, которое она устраняет. *Что станет хуже, если вернуть привычный способ?*
- [ ] **R1.2** Результат автоматизации виден до применения или исправляется; при отказе технологии задачу можно закончить иначе.
- [ ] **R1.3** Знакомая механика заменена только там, где выигрыш объясним.

### 2. Полезность

- [ ] **R2.1** Для каждого ключевого сценария понятен момент получения ценности.
- [ ] **R2.2** Основное ежедневное действие находится в контексте, а не в глубине меню.
- [ ] **R2.3** Каждое обязательное поле и шаг действительно нужны именно сейчас.
- [ ] **R2.4** Данные не приходится вводить повторно; контекст сохраняется между шагами.
- [ ] **R2.5** Результат работает вне продукта: файл открывается, ссылка ведёт куда нужно, подтверждение содержит нужные сведения.
- [ ] **R2.6** Ключевой сценарий прошёл человек, не участвовавший в проектировании, без подсказок; места, где понадобилась помощь, записаны.

### 3. Эстетичность

- [ ] **R3.1** На каждом экране понятно, что главное; заметность элементов совпадает с их важностью.
- [ ] **R3.2** Группы читаются по интервалам; выравнивание устойчиво; значения взяты из токенов.
- [ ] **R3.3** Длинные названия, пустые и переполненные списки, чужие изображения не ломают композицию.
- [ ] **R3.4** Контраст текста — не ниже WCAG AA; вспомогательный текст читаем; при 200% ничего не обрезано и не перекрыто.
- [ ] **R3.5** Каждый акцентный цвет означает одно и то же везде.

### 4. Понятность

- [ ] **R4.1** На любом шаге видно, где я, что выбрано и как вернуться; работают адреса, «Назад», новая вкладка.
- [ ] **R4.2** Одна сущность — одно название по всему продукту; кнопки называют результат.
- [ ] **R4.3** Поиск называет свою область; фильтры видны и снимаются по отдельности; «нет данных» отличается от «нет совпадений».
- [ ] **R4.4** Подписи полей не исчезают; формат объяснён заранее; ошибка стоит у своего поля.
- [ ] **R4.5** Одна иконка — одно значение; кликабельное отличается от некликабельного.
- [ ] **R4.6** Недоступная команда объясняет, почему она недоступна.
- [ ] **R4.7** Каждое сообщение об ошибке говорит, что произошло и что делать дальше; нет обвинений и голых кодов.
- [ ] **R4.8** Продукт понятен без поясняющих подписей; пояснения остались только там, где без них ошибаются ([признаки И1–И8](AI_TELLS.md)).

### 5. Ненавязчивость

- [ ] **R5.1** Каждое модальное окно и подтверждение требует реального решения; обратимые действия отменяются, а не подтверждаются.
- [ ] **R5.2** Фоновые обновления не крадут фокус, не прыгают списком и не сбивают ввод.
- [ ] **R5.3** Анимации объясняют изменения; с уменьшением движения интерфейс остаётся понятным.
- [ ] **R5.4** Уведомления не дублируются, разделены по срочности и настраиваются.

### 6. Честность

- [ ] **R6.1** «Готово» и «Сохранено» появляются только после подтверждения; без сети видно, что сохранено локально, а что синхронизировано.
- [ ] **R6.2** Цена, последствия и необратимость видны до нажатия; подтверждение удаления называет объект.
- [ ] **R6.3** Прогресс не притворяется точным.
- [ ] **R6.4** Отказаться, отменить и отписаться так же легко, как согласиться.
- [ ] **R6.5** Предварительные, устаревшие и сгенерированные данные помечены.

### 7. Долговечность

- [ ] **R7.1** Нет одноразовых вариантов компонентов без записи решения.
- [ ] **R7.2** Изменённая навигация и названия имеют план перехода; старые ссылки работают.
- [ ] **R7.3** Свои данные можно получить и выгрузить.
- [ ] **R7.4** Компоненты выдерживают рост данных и длинные переводы.
- [ ] **R7.5** Нет модных приёмов без связи с задачей.
- [ ] **R7.6** Нет [признаков ИИ-дизайна](AI_TELLS.md): шаблонных цветов, шрифтов, карточек, обвязки, анимаций, выдуманного содержимого.

### 8. Тщательность

- [ ] **R8.1** У каждого экрана есть загрузка, пусто, нет совпадений, ошибка, успех, нет доступа, частичный результат.
- [ ] **R8.2** После исправимой ошибки введённое сохраняется; повторяется только неудачное.
- [ ] **R8.3** Весь сценарий проходится с клавиатуры; фокус виден; диалоги ловят фокус, закрываются по Esc и возвращают его.
- [ ] **R8.4** Автопроверка доступности без критических ошибок; элементы озвучиваются понятно; смысл не только в цвете.
- [ ] **R8.5** Всё, что перетаскивается, можно сделать и без перетаскивания.
- [ ] **R8.6** Даты, числа, переносы, длинные строки и языки выглядят корректно.
- [ ] **R8.7** Реализация совпадает с замыслом; расхождения записаны.
- [ ] **R8.8** У элементов управления есть все состояния, включая фокус и выполнение; в мелкие элементы легко попасть.
- [ ] **R8.9** Закрытие окна, Esc, «Назад» и уход со страницы не теряют несохранённые изменения молча.

### 9. Экологичность

- [ ] **R9.1** Изображения и видео не тяжелее, чем нужно для отображения; тяжёлое грузится по запросу.
- [ ] **R9.2** Нет лишних фоновых запросов и автопроигрывания.
- [ ] **R9.3** Сценарии работают на обычном устройстве и медленной сети.
- [ ] **R9.4** Понятно, сколько хранятся данные и как удаляются.

### 10. Как можно меньше дизайна

- [ ] **R10.1** У каждого элемента и шага есть работа; нет двух способов сделать одно и то же без причины и элементов для сброса того, что сбрасывается само.
- [ ] **R10.2** Ничего не спрятано так, что человеку нужно помнить, где это искать.
- [ ] **R10.3** Частое — на виду, редкое — раскрывается по необходимости.
- [ ] **R10.4** Налог на ценность ключевых сценариев записан и есть с чем сравнить после исправлений.
